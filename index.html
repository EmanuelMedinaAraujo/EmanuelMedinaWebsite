LoveNeverDies: encryption design

Who it is for

Bereaved families, often older and not tech-savvy, have to handle certificates of inheritance, a six‑week renunciation window, probate courts and wills, and share highly sensitive documents while doing it. The app turns this into a task list. The legal decision tree behind it has 141 nodes and 80 outcomes, written by the team’s lawyers, and the court lookup covers 611 probate courts.

Data flow

  • Each device generates hybrid ML-KEM-768 + X25519 (key exchange) and ML-DSA-65 + Ed25519 (signature) keypairs. Keys are non-extractable and never leave the device.
  • Key hierarchy: device key → case key → per-item data keys (AES-256-GCM), with separate keys for private items and the vault.
  • Offline-first: writes land in an IndexedDB queue and sync as ciphertext to Supabase Postgres, guarded by row-level security. Clerk issues the JWTs.
  • Sync is a version check plus a delta fetch above a per-case watermark, triggered by a Realtime “doorbell” with 30-second polling as fallback.
  • The vault key is Shamir-split so that ⌈2n/3⌉ of n relatives must cooperate. An Edge Function verifies both signatures before release.
  • Device pairing uses an 8-character rendezvous code plus a spoken 6-digit check derived from both public keys.

Choices and trade-offs

  • Hybrid KEM and signaturesAn attacker has to break a classical and a post-quantum algorithm.Trade-off: 64 extra bytes per signature.
  • Per-item data keysKey rotation re-wraps 32-byte keys instead of re-encrypting payloads: “a few kilobytes instead of hundreds of megabytes”.
  • The vault opens on proof of reconstruction, not on a release counterA validly signed but bogus share can’t flip a living person’s case.
  • No recovery phraseAccess is re-granted by relatives rather than restored from a secret.Trade-off: losing your only device means waiting for a relative to re-grant access.
  • No statute citations in the UIThe app should guide, not read as legal advice (ADR-0003).

Key rotation and sync

  • Concurrent key rotation: a 2-minute row-locked lease plus compare-and-swap on the key generation.
  • Sync ordering: bigserial was rejected because it skips updates and can commit out of order. It was replaced by a per-case counter under row lock and a trigger that forbids un-deleting tombstones.
  • A threat model that documents ten accepted limits explicitly, e.g. that same-origin XSS could decrypt everything.

Built with React 19, TypeScript, Vite, PWA, Supabase, Postgres RLS, Edge Functions, Clerk, @noble/post-quantum, WebCrypto, Vitest, PGlite and Playwright.

SchafPlay: peer-to-peer design

The goal

Play Schafkopf with a friend, with AI filling the empty seats, and no accounts, servers or signalling infrastructure to run.

Pairing two phones

  • The host creates a WebRTC offer and data channel. The SDP is minified, deflated and base64url-encoded into a compact invite code.
  • The guest receives it by paste, QR code or link and returns a reply code. The host accepts it and the data channel opens.
  • The game engine runs only on the host. A single processAction entry point validates every move, and AI moves take the same path.
  • Before anything is sent, redactStateFor replaces other players’ hands with placeholders and hides the Sauspiel partner until it’s revealed.
  • Every game is recorded to IndexedDB for trick-by-trick replay analysis.

Choices and trade-offs

  • No signalling server and no STUNZero infrastructure to run: two browsers and a code.Trade-off: LAN-first by design, with Tailscale documented for remote play.
  • A host-authoritative engine with one redaction boundaryOpponents’ hands never go over the wire, and the host overwrites the guest’s player ID, so values from the wire are never trusted.
  • Minify SDP before compressingOnly per-session entropy is kept (ICE credentials, DTLS fingerprint, candidates) and the rest is regenerated on decode, which keeps invite codes compact.
  • rules.ts as the single source of legalityThe engine, UI and AI can never disagree about which card is playable.
  • Pause on disconnectRe-pairing attaches a fresh transport to the same game session.

Testing and trust

  • A seeded, dependency-free shuffle (mulberry32 + Fisher–Yates), so automated end-to-end runs can reproduce identical deals.
  • Treating the host as potentially hostile: every inbound string path is sanitised, and avatars are the only peer data that reaches an <img>.
  • A data-channel heartbeat detects dead links.

Built with React 19, TypeScript, Vite, WebRTC, CompressionStream, IndexedDB, Service Worker, Playwright and GitHub Actions.

Bachelor thesis: method and results

The question

Map an arm’s geometry (Denavit–Hartenberg parameters) and a goal position to joint angles. Compare direct versus probabilistic outputs, and feed-forward versus recurrent architectures.

Training without labelled answers

  • Random DH parameters (link lengths 0.3–0.5) and reachable goals are generated synthetically, so one model learns arbitrary arms rather than a single robot.
  • Input: DH parameters plus goal. Output: (sin, cos) per joint, converted to angles with atan2.
  • Loss: end-effector-to-goal distance through differentiable forward kinematics, so training needs no labelled angles.
  • Compared MLP, LSTM, hybrid MLP+LSTM and probabilistic heads (Normal, Beta, two-peak), and PPO, a reinforcement-learning method (Stable-Baselines3).
  • Hydra configs → Optuna hyperparameter search → Weights & Biases tracking → bootstrapped summaries.

10,000 test problems, 5 runs, accuracy is the share of problems solved within 0.01 tolerance. Best direct MLP from Optuna: hidden layers [2048, 256, 2048], Adam, batch size 512.

What I learned

  • IK is multimodal (several joint configurations reach the same goal), which motivated the two-peak distribution heads. In practice the direct model handled it best.
  • Some probabilistic variants collapsed entirely (Beta: 5–8%), a useful negative result for choosing practical IK models.
  • PPO needed 45–50 million training steps and still solved only 56–70%: reinforcement learning is built for multi-step tasks, while IK is a single prediction.
  • Solo project: about 4.7k lines of Python, 217 commits.

Built with Python, PyTorch, Stable-Baselines3, Gymnasium, Hydra, Optuna and Weights & Biases.
