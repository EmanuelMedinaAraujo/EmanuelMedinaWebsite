How it works · Aug 2026

LoveNeverDies

In plain words

When someone dies, their family suddenly faces deadlines, forms and court visits, often while grieving. LoveNeverDies turns that into a simple, guided to-do list that the whole family can share. Because the information is so personal, it is locked on the family's own phones before it is sent anywhere: the server only ever stores scrambled data that it cannot read.

  • 10days from idea to working app
  • 141step legal decision tree, written with the lawyers on the team
  • 0readable data on the server: it only stores ciphertext
  • 611probate courts, found from 10,813 postcodes

How it is built

  • Each device creates its own key pairs (ML-KEM-768+X25519 for encryption, ML-DSA-65+Ed25519 for signatures). They cannot be exported.
  • Keys are layered: the device key opens the case key, which opens a separate key for every item (AES-256-GCM). Private items and the vault have their own keys.
  • Changes wait in an offline queue, then reach Supabase Postgres as ciphertext, protected by row-level security. Clerk handles login.
  • Devices sync by fetching only what changed, nudged by a realtime signal with a 30-second fallback.
  • Pairing a new device uses an 8-character code plus a 6-digit number both people read out loud, derived from both public keys.

Key decisions

Two encryption algorithms at once
Classic and post-quantum algorithms are combined, so an attacker has to break both. Trade-off: 64 extra bytes per signature.
A key for every item
Rotating keys only re-wraps small 32-byte keys instead of re-encrypting every file: kilobytes instead of hundreds of megabytes.
A vault that needs the family together
The vault key is split between relatives (Shamir secret sharing, ⌈2n/3⌉ of n). It only opens on proof that the key was really rebuilt, so one forged share cannot open it.
No recovery phrase
Keeps things simple for people who are not technical. Trade-off: losing your only device means a relative has to grant access again.

Hard parts

  • Two devices rotating keys at the same moment: solved with a 2-minute lock on the row plus a compare-and-swap on the key generation.
  • Database auto-increment IDs can commit out of order, which breaks sync. They were replaced by a per-case counter under a row lock.

How it works · 2026

SchafPlay

In plain words

Most online games need a company server in the middle. SchafPlay does not: one phone hosts the game and the other joins by scanning a QR code or opening a link, and from then on they talk to each other directly over the local Wi-Fi. The host phone deals the cards and only ever sends each player their own hand, so nobody can cheat by peeking.

  • 0servers: the app is just static files on GitHub Pages
  • 1QR code or link to connect two devices
  • 2computer players at the table
  • v1.0.0released and live

How it is built

  • The host creates a WebRTC offer, then trims, compresses and encodes it into a short invite code that fits in a QR code.
  • The guest receives it by paste, QR or link and sends back a reply code; accepting it opens a direct data channel.
  • Every move, human or computer, goes through one entry point in the host's game engine and is checked against the same rules.
  • Before anything leaves the host, other players' hands are replaced by placeholders and the hidden partner stays hidden until revealed.
  • Games are recorded on the device for a trick-by-trick replay.

Key decisions

No server at all
Nothing to operate, pay for or keep secure. Trade-off: it is made for the same network; remote play works through Tailscale, as documented.
The host is the referee
The host even overwrites the guest's player ID, so nothing arriving over the connection is trusted blindly.
Short invite codes
Only the parts of the connection offer that change per session are kept; the rest is rebuilt on arrival, which keeps codes small enough for a QR code.
One rulebook
A single rules module decides what is legal for the engine, the interface and the computer players.

Hard parts

  • A seeded shuffle without dependencies makes every deal reproducible, which keeps automated games deterministic.
  • Every piece of text coming from the other device is sanitised, and a heartbeat notices dropped connections so the game can pause and resume.

How it works · Bachelor thesis · 2024

How robot arms learn to reach

In plain words

If you want a robot arm to touch a point, you have to tell each joint how far to turn. Working that out is called inverse kinematics. I trained different neural networks to do it for arms of any shape, then tested them on 10,000 new reaches. The simplest network was both the most accurate and the fastest: it got every single one right, in about 0.16 milliseconds each.

  • 100%of 10,000 test reaches solved within 0.01 tolerance
  • ~155 µs(0.16 ms) per answer, the fastest of all models
  • 2 & 3joint arms with random lengths
  • 5seeded runs per model for a fair comparison

Key decisions

Learn from where the hand lands
The network is scored on how far the arm's hand ends up from the goal, computed with differentiable forward kinematics, so no "correct" joint angles are needed for training.
The arm's shape is an input
The arm's geometry (DH parameters) is fed in, so one model handles many different arms instead of a single robot.
Angles as sine and cosine
Each joint is predicted as (sin, cos) and converted with atan2, which avoids a jump where angles wrap around.
An honest comparison
The simple network won on accuracy and speed per answer. It did not win on training time (~579 s vs 248–378 s for some variants).

Hard parts

  • Most points can be reached in more than one way (elbow up or down), which motivated output distributions with two peaks.
  • Some probabilistic models collapsed: the Beta model only reached 5–8%.
  • Hydra configuration, Optuna hyperparameter search (best network: 2048-256-2048, Adam, batch 512), Weights & Biases tracking and bootstrapped summaries, plus a reinforcement-learning (PPO) baseline in Stable-Baselines3.
